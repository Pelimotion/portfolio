### 1.3 Dívidas — lista priorizada

**🔴 Dívidas de USABILIDADE (impacto direto na produtividade)**
1. **`window.prompt` + `window.confirm` para fluxos críticos** ([AssetsPanel.jsx:41](projetos-app/src/components/storage/AssetsPanel.jsx#L41) cola URL de Drive; `Sidebar.jsx:70` confirma exclusão de projeto). Anti-padrão direto (red flag do `AI_AGENT_BRIEFING.md`).
2. **Calendário só tem visão de mês.** Sem day / week / agenda → inviável para time-blocking real. Cron/Notion Calendar tem 4 views e atalhos `T`/`J`/`K`/`G`.
3. **Atalhos de teclado mínimos.** Só `⌘K` e `⌘\` mapeados. Linear tem `X` select, `Space` peek, `Shift+↑↓` mover, `G` group-by; Cron tem `T/J/K`. O potencial está desperdiçado.
4. **Counters fake hardcoded no card** (`MessageSquare 2` / `Paperclip 1` em `EntityCard.jsx:225-230`). Quebra confiança quando o usuário percebe.
5. **Filtros e agrupamento ausentes nas views.** Kanban agrupa só por status; sem grupo-por-prioridade, prazo, dono, label.
6. **Sem peek/preview de card.** Para olhar uma cena hoje, é clique → nova rota → volta.
7. **Sem multi-select de cards** (mover/atribuir em lote).
8. **Sem skeleton states por componente** — fallback é um único `animate-pulse` genérico.
9. **Drive: criar conexão é `window.prompt("Cole a URL")`.** O `FolderPickerModal` existe — não está ligado ao primeiro vínculo.

**🟡 Dívidas VISUAIS (qualidade percebida)**
1. **Inconsistência de tipografia.** Misturas de `text-[10px]` `font-black uppercase tracking-wider` (estilo "OS militar") com `text-[13px] font-medium` (estilo Notion). O sistema oscila entre dois conceitos.
2. **`font-black` em demasia.** Cards usam `font-black` para títulos `text-[13px]` — Notion usa `font-semibold` para a mesma hierarquia.
3. **Densidade visual irregular.** Topbar do Dashboard tem 64px de altura com 5 widgets diferentes (ícone hub + Equipe + Search + Novo Projeto + Avatar) — Linear/Notion mantêm topbar em ~44px.
4. **Hover states fortes mas inconsistentes.** Alguns usam `hover:scale-[1.02]`, outros `-translate-y-0.5`, outros nada.
5. **Color tokens duplicados.** `surface-2` no Tailwind via `var(--surface-2)` em strings literais — não há classe utilitária `bg-surface-2`. Frequência alta de `bg-[var(--surface-2)]`.
6. **Sem grid de 8px estrito.** Padding usa `px-3.5`, `py-2.5`, `gap-2.5` — fora da escala `--space-*` já definida.

**💀 MAIORES DÍVIDAS (uma de cada categoria)**
- **Maior dívida de USABILIDADE:** **falta de calendário completo** (day/week/agenda + time-blocking + atalhos). É a feature que mais distancia o app dos benchmarks (Cron/Notion Calendar, Fantastical).
- **Maior dívida VISUAL:** **inconsistência tipográfica + uso excessivo de `font-black`/`uppercase tracking-wider`** — passa sensação de "dashboard de jogo" em vez de "ferramenta de produtividade". Notion/Linear usam ~2 pesos (regular + semibold) e MUITO pouco uppercase.

## 2) RESEARCH BRIEF

> Padrões abaixo são citados das fontes verificadas via WebSearch / WebFetch listadas em **Sources** no final. Quando o padrão veio de snippet de busca (não fetch direto da página inteira), está marcado `[snippet]`.

### 2.1 Visual / Design System — referência: **Notion**
1. **3 famílias tipográficas selecionáveis por página** (Default sans, Serif, Mono) — usuário decide tom da página, não o app. `[snippet]` Fonte: [notion.com/help/customize-and-style-your-content](https://www.notion.com/help/customize-and-style-your-content)
2. **Paleta de 10 cores fechadas para ícones**, com tons mais saturados que os de texto/fundo — disciplina contra "rainbow UI". Fonte: [matthiasfrank.de/en/notion-colors](https://matthiasfrank.de/en/notion-colors/)
3. **Espaçamento via blocos** (callouts, dividers, colunas) — composição em vez de margins ad-hoc. `[snippet]`
4. **Hierarquia tipográfica enxuta:** Title, H1, H2, H3, body. Sem mais que 4 pesos no app inteiro.
5. **Princípio "design system = standards + reusable elements"** — Notion publicou guia interno reforçando consistência sobre criatividade individual. Fonte: [notion.com/blog/how-to-create-a-design-system](https://www.notion.com/blog/how-to-create-a-design-system)

**Tradução para projetos-app (motion design / cenas / peças):**
- Adotar **2 pesos só** (`font-medium` 500 + `font-semibold` 600). Banir `font-black` exceto em métricas grandes do dashboard.
- Fechar paleta de cores de status em **9 opções** (já temos em `core/colors.js` — auditar e ratificar).
- `tracking-wider uppercase` reservado para LABELS de eyebrow (≤ 12 chars), **nunca** em textos de UI corrente.

**Veredito:** **ADOTAR** integralmente. Custo baixo, impacto visual alto. Já temos tokens; falta disciplina de uso.

### 2.2 Kanban — referências: **Linear, Trello, Height**
Padrões concretos verificados em [linear.app/docs/board-layout](https://linear.app/docs/board-layout):

1. **Card sem descrição** — só título + 5–8 metadata em badges. (Hoje nosso `comfortable` mostra título + status + prioridade + tags + cover + footer rico — está mais carregado que Linear.)
2. **`Space` para "peek"** — preview lateral sem perder contexto da board.
3. **`Shift+Option+↑/↓` move issue para topo/base da coluna** — atalhos para evitar arrasto em coluna longa.
4. **`X` seleciona + `Shift+X` multi-select** — operações em lote.
5. **`T` colapsa/expande swimlanes**; **`S` muda coluna (status)**.
6. **Group-by configurável**: Status (default), Priority, Project, Cycle, Label, Assignee. **Cada grupo gera as colunas dinamicamente.**
7. **Swimlanes** = sub-grupos horizontais (por owner, por cycle, por project) — colapsáveis.
8. **Scroll horizontal com `Shift+wheel`** ou arrasto em espaço vazio da board.
9. **Hide/show colunas** com possibilidade de soltar card numa coluna oculta.

**Tradução para projetos-app:**
- Hoje o kanban agrupa só por status. Habilitar group-by por qualquer propriedade `select|status|people|date` é destravar Linear-grade.
- Atalhos `X` / `Shift+X` / `Space` faltam — são o que diferencia produtividade real de "kanban bonito".
- Swimlanes são overkill para BETA — adiar.

**Veredito:** **ADOTAR** peek (`Space`), atalhos de seleção/movimento, group-by. **ADAPTAR** densidade do card (remover counters fake, simplificar para Linear-style). **IGNORAR** swimlanes nesta rodada.

Referências secundárias: [Linear Web Kanban — Mobbin](https://mobbin.com/explore/screens/77a9dcea-7020-44ba-9e26-f30a86d92bf4) (screenshots), [LogRocket DnD best practices](https://blog.logrocket.com/ux-design/drag-and-drop-ui-examples/) (drop zones grandes, drag-handle dedicado em telas densas).

### 2.3 Calendário — referências: **Cron / Notion Calendar, Fantastical**
Padrões verificados em [notion.com/help/guides/getting-started-with-notion-calendar](https://www.notion.com/help/guides/getting-started-with-notion-calendar) e blog correlato:

1. **4 views: day / week / month / schedule (agenda)** — não opcional. `[snippet]`
2. **`T` volta para hoje · `J/K` próxima/anterior semana ou mês · `←/→` mover entre dias · `N` cria evento · `G` go-to-date.** Sistema vim-like. Fonte: [Cron global keyboard shortcuts](https://cronhq.notion.site/Global-keyboard-shortcuts-e933a55e7fb648028b09cedf933d3e76)
3. **Event blocking entre calendários múltiplos** — bloqueio automático para evitar conflito work/personal. `[snippet]`
4. **Drag-and-drop de eventos no time-grid** atualiza a fonte de dados (database Notion ↔ evento). Princípio: calendário como **superfície de edição visual** de uma fonte de dados.
5. **`S` compartilha disponibilidade · `F` agenda com colega** — comandos de alto nível.

**Tradução para projetos-app:**
- Cada **cena com `deadline` ou `startDate`** já é um evento candidato — calendário deve agregar **todos os projetos** do usuário (não só do projeto aberto). O `CalendarView` atual em `DatabaseRenderer.jsx:794` faz isso parcialmente (load global), mas só em vista mês.
- Time-blocking em projetos motion design = bloquear horas/dias por cena (render, revisão, sound). Útil porém pesado — Fase D mínima viável.
- O export "Adicionar ao Google Calendar" já existe (boa!). Próximo passo: 2-way sync? Adiar — começa unilateral (read-only no Google Calendar).

**Veredito:** **ADOTAR** as 4 views, atalhos `T/J/K/N/G`, drag-to-reschedule de evento. **ADAPTAR** time-blocking para granularidade dia, não hora (motion não exige minuto). **IGNORAR** event blocking entre múltiplos calendários (escopo demais).

Refs adicionais: [Cron Changelog](https://www.cron.com/changelog), [Notion Calendar blog](https://www.notion.com/blog/notion-calendar-helps-you-manage-your-time-more-effectively).

### 2.4 Navegação / IA — referências: **Linear, Notion, Superhuman**
Padrões verificados em [blog.superhuman.com/how-to-build-a-remarkable-command-palette](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/):

1. **`⌘K` é universal** — o mesmo atalho abre/fecha de qualquer lugar; restaura foco anterior ao fechar.
2. **Fuzzy match com `command-score`** — "lnik" encontra "Link".
3. **Aliases para comandos** — "Archive" alias de "Mark Done".
4. **Score = fuzzy × peso por comando × recência de uso** — comandos frequentes sobem.
5. **Contexto influencia ranking** — comandos disponíveis mudam conforme view atual (estamos numa cena? aparecem "Mover para...", "Atribuir a...", "Definir prazo...").
6. **Ícone por comando** + **cortar último item visualmente** para sugerir scroll. `[fetch]`
7. **Toda ação clicável também é comando** — sem ações órfãs.
8. **Atalho exibido ao lado do comando no palette** — aprendizagem passiva (regra famosa do Superhuman). Fonte: [Speed as the Product — Superhuman](https://blakecrosley.com/guides/design/superhuman)

**Tradução para projetos-app:**
- Hoje `CommandPalette` faz busca de páginas (search-only). Falta o lado **comando**: "Criar projeto", "Criar cena", "Mudar status", "Toggle theme", "Ir para Hoje".
- Migrar para a lib **`cmdk`** (cinco mil estrelas, mantida por Paco Coursey, é o que Linear usa em produção) **OU** estender o palette atual. `cmdk` traz fuzzy + ARIA + agrupamento out-of-the-box.

**Veredito:** **ADAPTAR** — manter o palette atual mas adicionar comandos + contexto + atalhos visíveis. **ADOTAR** `cmdk` se aceitarmos uma dependência (≈10kb, headless).

Refs adicionais: [Retool Command Palette design](https://retool.com/blog/designing-the-command-palette), [Command Palette UX Patterns — Bootcamp](https://medium.com/design-bootcamp/command-palette-ux-patterns-1-d6b6e68f30c1).

### 2.5 Integração com Drive — referência: **Notion + Google Drive**
Padrões verificados em [notion.com/integrations/google_drive](https://www.notion.com/integrations/google_drive):

1. **"Paste as preview"** — usuário cola URL do Drive em qualquer página, escolhe entre link cru ou preview embed. `[snippet]`
2. **Comando `/google`** in-line abre seletor nativo que **navega pelas pastas do Drive** sem sair do Notion. `[snippet]`
3. **Embed block é interativo** mas **read-only**; edição abre Drive em nova aba.
4. **Updates do Drive refletem no preview em "tempo real"** — não é cache estático.
5. **Limitações conhecidas:** preview do Sheets pode mostrar área errada da planilha; Notion ainda exige clique para editar.

**Tradução para projetos-app:**
- Hoje o vínculo de pasta-raiz é `window.prompt("Cole a URL")` em [AssetsPanel.jsx:41](projetos-app/src/components/storage/AssetsPanel.jsx#L41). Precisamos do equivalente ao "Paste as preview" — abrir um modal com **opções claras** (link, embed, sincronizar como sub-database).
- "Sincronizar Estrutura" já existe (`onSyncStructure` no `AssetsPanel`). Falta feedback visual em tempo real (toast com progresso, não só spinner em texto).
- Para cenas: cada cena deveria ter "slot" para 1+ pastas/arquivos do Drive. `useDriveSlots` + `DriveSlotCard` já existem — falta **affordance de drop**: arrastar URL do navegador para o card.

**Veredito:** **ADOTAR** padrão "Paste as preview" via Radix Dialog (substituir os `window.prompt`). **ADAPTAR** o sync para mostrar progresso. **ADOTAR** drag-from-browser para vincular Drive.

### 2.6 Microinterações e fluidez — referências: **Linear, Superhuman, Arc**
Padrões consolidados das fontes:

1. **Regra dos 100ms** (Superhuman internamente mira 50–60ms) — toda interação até esse limite é percebida como "instantânea". Fonte: [Superhuman: Speed as the Product](https://blakecrosley.com/guides/design/superhuman) `[snippet]`
2. **Optimistic UI**: aplica mudança no cliente, sincroniza com servidor em background, rollback em erro. (O nosso `DatabaseRenderer` já faz isso em `handleValueChange` e `handleStatusChange` — manter.)
3. **Easing curves não-lineares.** Enter: ease-out (rápido→devagar). Exit: ease-in. Mudança de estado: ease-in-out. Fonte: [CorsoUX UI Animations 2026](https://courseux.com/ui-animations/) `[snippet]`
4. **"Motion minimalism"** (Dan Saffer): microinteração existe para sinalizar, não decorar. Fonte: [Manav Kaushal — Motion is Meaning](https://medium.com/@manavkaushal756/motion-is-meaning-micro-interactions-ux-3131b4d95a05) `[snippet]`
5. **Productive motion** (Carbon Design System): animações curtas (100–200ms) para tarefas focadas, mais longas (300–500ms) só para onboarding/celebração. Fonte: [Carbon Motion](https://carbondesignsystem.com/elements/motion/overview/)
6. **Skeleton states por componente**, não por página — diminui CLS e percepção de wait.

**Tradução para projetos-app:**
- Animações `hover:scale-[1.02]`, `hover:-translate-y-0.5` estão OK, mas precisam de easing consistente. Hoje Tailwind aplica `transition-all` sem curva customizada — adicionar `ease-[cubic-bezier(0.2,0,0,1)]` (curva do Material Expressive / Linear).
- `framer-motion` está instalado mas pouco usado. Bom candidato para: card peek (slide-in lateral), command palette (já tem `animate-in`), reordenação de coluna no kanban (layout animation).
- Skeleton: criar `<EntityCardSkeleton />`, `<KanbanColumnSkeleton />`, `<CalendarSkeleton />`.

**Veredito:** **ADOTAR** regra 100ms como métrica de aceitação. **ADOTAR** easing tokens + skeletons. **ADAPTAR** framer-motion para 2-3 momentos chave (peek, layout do kanban). **IGNORAR** motion "celebrativo" (confetti, etc.) — não combina com tom de ferramenta.

## 3) PLANO DE IMPLEMENTAÇÃO

> Princípio: **incremental, rotulável para rollback**. Cada fase é uma branch + PR. Sistema está em produção com a equipe → nenhuma fase pode quebrar o que existe.

### Fase A — Design System base
**Escopo:**
- Auditar `index.css` tokens vs. classes Tailwind. Criar utilitários: `bg-surface-1..3`, `border-subtle/default/strong`, `text-status-*`.
- Definir escala tipográfica enxuta: `text-display | text-h1 | text-h2 | text-h3 | text-body | text-small | text-caption | text-eyebrow`. 2 pesos só: 500 + 600.
- Banir `font-black` (codemod). Banir `uppercase tracking-wider` fora de `text-eyebrow`.
- Documentar em `projetos-app/docs/DESIGN_TOKENS.md` (criar).
- Componentes primitivos faltantes em `src/components/ui/`: `Button` (4 variantes), `Input`, `Select`, `Badge`, `Card`, `Skeleton`, `Tabs`, `Toggle` — usando Radix onde aplicável.

**Por quê:** Inconsistência tipográfica é a maior dívida visual. Sem primitives, cada feature reinventa estilos.
**Arquivos:** `projetos-app/src/index.css`, `projetos-app/tailwind.config.js`, `projetos-app/src/components/ui/*` (novos).
**Esforço:** **M** (semana de trabalho).
**Risco:** **médio** — codemod de `font-black`/`uppercase` toca muitos arquivos; precisa PR atômico.
**Critério de aceite:** Storybook ou página `/dev/tokens` mostra todos os primitives; busca por `font-black` no `src/` retorna 0; visual da Sidebar e Dashboard mantém-se ≥ 95% igual após codemod.

---

### Fase B — Navegação / Command Palette estendido
**Escopo:**
- Migrar `CommandPalette` para `cmdk` (ou estender atual, ver Decisão #2).
- Adicionar **comandos** (não só busca): `Criar projeto`, `Criar cena`, `Mudar status`, `Atribuir a...`, `Ir para Hoje`, `Toggle theme`, `Toggle sidebar`.
- Mostrar **atalho ao lado de cada comando** (aprendizagem passiva).
- Comandos **contextuais** por view (numa cena, "Mover para coluna...", "Definir prazo...").
- Atalhos globais novos: `G then P` (go projects), `G then C` (calendar), `?` (cheat sheet de atalhos).

**Por quê:** Maior multiplicador de produtividade. Palette atual é só search — desperdício do potencial.
**Arquivos:** `projetos-app/src/components/ui/CommandPalette.jsx`, `projetos-app/src/stores/useUIStore.js`, `projetos-app/src/hooks/useKeyboardShortcuts.js` (novo), `projetos-app/src/components/ui/ShortcutCheatSheet.jsx` (novo).
**Esforço:** **M**.
**Risco:** **baixo** — palette é isolado, fácil de fazer rollback.
**Critério de aceite:** `⌘K` lista ≥ 12 comandos; `?` mostra cheat sheet; criar projeto via palette < 3 toques (`⌘K → "novo" → Enter`).

### Fase C — Kanban refinado
**Escopo:**
- **Quebrar `DatabaseRenderer.jsx`** (1097 linhas) em `views/KanbanView.jsx`, `views/TableView.jsx`, `views/ListView.jsx`, `views/CalendarView.jsx` + `DatabaseRenderer.jsx` orquestrador.
- **Group-by configurável** (Status / Prioridade / Owner / Label / Prazo).
- **Peek `Space`** — Radix Dialog lateral com props da entidade, sem trocar rota.
- **Atalhos** `X` select, `Shift+X` multi-select, `Shift+Opt+↑/↓` mover topo/base.
- Remover counters fake (`MessageSquare 2`, `Paperclip 1`) ou ligar a dados reais.
- Limpar densidade do card: cover opcional (só projetos), no padrão sem cover; reduzir uso de uppercase.

**Por quê:** Kanban é a view principal; alinhar com Linear destrava produtividade real.
**Arquivos:** `projetos-app/src/components/database/DatabaseRenderer.jsx`, `projetos-app/src/components/database/views/*` (novos), `projetos-app/src/components/database/EntityCard.jsx`, `projetos-app/src/components/database/EntityPeek.jsx` (novo).
**Esforço:** **L**.
**Risco:** **alto** — kanban é o coração do app. Plano: 3 PRs separados (split → group-by → atalhos+peek).
**Critério de aceite:** Drag de card permanece ≤ 100ms percebido; group-by por Prioridade gera colunas Urgente/Alta/Média/Baixa em < 200ms; peek abre em `Space` sem flicker.

### Fase D — Calendário completo
**Escopo:**
- 4 views: **Mês (existente) · Semana · Dia · Agenda**.
- Atalhos: `T` hoje, `J/K` próximo/anterior, `←/→` navegar, `N` novo evento, `G` go-to-date.
- Drag-to-reschedule: arrastar cena na grid → atualiza `deadline` (optimistic).
- Filtro "Apenas meus projetos" / "Toda a equipe" no header do calendário.
- Manter export "Adicionar ao Google Calendar" (já existe).

**Por quê:** Maior dívida de usabilidade identificada. Sem week/day views, não há time-blocking.
**Arquivos:** `projetos-app/src/components/database/views/CalendarView.jsx` (extraído da Fase C), `projetos-app/src/components/calendar/*` (preencher a pasta vazia: `WeekView`, `DayView`, `AgendaView`, `CalendarHeader`, `CalendarKbd`).
**Esforço:** **L**.
**Risco:** **médio** — depende de Decisão #3 (lib calendar). Custom feito sobre date-fns é trabalhoso mas flexível; FullCalendar é poderoso mas pesado.
**Critério de aceite:** Trocar entre 4 views em < 100ms; arrastar uma cena no calendário muda `deadline` no DB; `T` volta para hoje em qualquer view.

### Fase E — Integração Drive polida
**Escopo:**

**Por quê:** Drive é fluxo de trabalho primário (motion files são pesados, não cabe upload no Bunny). Hoje o vínculo inicial parece amador.
**Arquivos:** `projetos-app/src/components/storage/AssetsPanel.jsx`, `projetos-app/src/components/storage/DriveConnectionModal.jsx` (novo), `projetos-app/src/components/storage/DriveSlotCard.jsx`, `projetos-app/src/hooks/useDriveSlots.js`.
**Esforço:** **M**.
**Risco:** **baixo** — drive layer está isolado.
**Critério de aceite:** Conectar Drive sem nenhum `window.prompt`; drop de URL no card cria slot em < 300ms; toast mostra progresso de sync por pasta.

### Fase F — Microinterações e performance percebida
**Escopo:**
- Easing tokens em `tailwind.config.js`: `--ease-in-out-expressive: cubic-bezier(0.2, 0, 0, 1)`. Aplicar a hovers e transitions globalmente.
- Skeleton states por componente: `<EntityCardSkeleton/>`, `<KanbanColumnSkeleton/>`, `<CalendarSkeleton/>`.

**Por quê:** Última camada de polimento. Sem isto o app fica "bom" mas não "delightful".
**Arquivos:** `projetos-app/tailwind.config.js`, `projetos-app/src/components/ui/skeletons/*` (novos), `projetos-app/src/lib/perf.js` (novo), `projetos-app/src/components/ui/Toast.jsx`.
**Esforço:** **M**.
**Risco:** **baixo**.
**Critério de aceite:** Mudar status de card mede < 100ms até render; nenhum loading state mostra só "Inicializando..." em texto.

Detalhes preservados abaixo para referência.

### Decisão 1 — Biblioteca de calendário *(bloqueia Fase D)*
**Opções:**
- **(a) Custom sobre `date-fns`** — máximo controle visual, igual ao tom Pelimotion; ~L de esforço; sem dependência pesada.
- **(b) `react-big-calendar`** — pronto, dia/semana/mês/agenda, mas visual genérico e CSS dificil de customizar profundamente.
- **(c) FullCalendar (React)** — mais completo do mercado, mas ~200kb e visual fora do tom.
- **Recomendado: (a)** — alinhado com o resto do app vanilla-craft. Vamos sofrer 1-2 semanas, mas o resultado fica único.

### Decisão 2 — Migrar `CommandPalette` para `cmdk`? *(bloqueia Fase B)*
**Opções:**
- **(a) Manter custom** — controle total; precisamos implementar fuzzy + ARIA na mão.
- **(b) Migrar para `cmdk`** (Paco Coursey, mesmo lib do Linear) — headless, ~10kb, fuzzy + ARIA + grouping built-in.
- **Recomendado: (b).** A implementação atual já é boa mas vai dobrar de complexidade quando adicionar comandos contextuais. `cmdk` é a "estrada principal".

### Decisão 3 — Adotar `shadcn/ui` formalmente? *(impacta toda Fase A)*
Hoje os componentes parecem shadcn-inspired mas não há `components.json` nem CLI configurada. Opções:
- **(a) Adotar CLI do shadcn** — `npx shadcn@latest add button input...`; código vai pra `src/components/ui/` automaticamente. Mantemos ownership do código.
- **(b) Continuar manual** — escrever cada primitive na mão usando Radix.
- **Recomendado: (a)** — é exatamente o caso de uso do shadcn. Não adiciona dependência runtime (só dev-time copy).

### Decisão 4 — Quebrar `DatabaseRenderer.jsx` agora ou depois? *(impacta Fase C)*
- **(a) Quebrar antes de adicionar group-by** (PR separado, "refactor only").
- **(b) Quebrar junto** com a feature de group-by.
- **Recomendado: (a)** — 1097 linhas misturam 4 views + DnD + estado. Refactor isolado tem rollback claro.

### Decisão 5 — Escopo da Fase A: codemod de `font-black` agora ou gradual? *(bloqueia Fase A)*
- **(a) Codemod atômico** (1 PR substitui todos os `font-black` por `font-semibold` + ajustes pontuais).
- **(b) Gradual** (cada nova feature usa o novo padrão; código antigo migra "quando tocar").
- **Recomendado: (a)** se conseguirmos hora de QA dedicada. Senão (b) com lint rule que avisa em arquivos novos.
